# Supabase egress audit — September 18, 2026

Status: first patch implemented locally after user approval. No database, deployment, or billing settings changed. The original audit/proposal follows; implementation details are recorded below.

Implemented: summary reads on article/topic listings and both analytics pages; explicit sermon fields; removal of unused audit snapshots/moderation liker rows/metrics columns; 60-second public data caching with editorial invalidation; and visibility-aware notification polling with overlap protection and failure backoff. Login screens do not poll; changing the signed-in profile restarts polling. Existing layouts, styles, full article/editor content, archive selection, and personalized interactions are preserved.

Verification: `npm run lint`, `node --experimental-vm-modules --test tests/egress.test.mjs` (eight fixture-based checks), and `npx next build --webpack --experimental-build-mode compile`. The compile-only build avoids prerendering the site against the restricted database. Tests use a controlled cache adapter and database fixtures; production cache behavior and bandwidth savings still need measurement after deployment. No live database/media fetches were deliberately performed for verification.

Deferred: database pagination/filtering, analytics aggregation, image variants, slimmer public author fields, and SQL related-content ranking. These were identified as follow-up work in the approved first-patch proposal, not included in this implementation.

The supplied notice reports 5.79 GB against 5.5 GB, with requests restricted until September 22, 2026. Optimizations reduce future traffic; they do not remove already consumed bandwidth. Supabase documents that restrictions clear at the next billing cycle or through an applicable billing change: [Manage Egress usage](https://supabase.com/docs/guides/platform/manage-your-usage/egress).

This is a source audit of application queries, API routes, their callers, media delivery, auth clients, migration definitions, and maintenance scripts. No production queries, media downloads, or builds were run. The authenticated Usage Dashboard and deployed request logs were not available, so actual bytes, traffic frequency, deployed schema, and the dominant service remain unverified. Source findings below are confirmed; impact rankings are estimates.

## Concrete first patch for approval

1. In `app/articles/page.jsx` and `app/topics/[slug]/page.jsx`, request `getPublications({ summary: true })`; keep subsequent filters working. Database-side topic filtering can follow in the same patch if its descendant handling is covered.
2. In `src/lib/data.js`, remove audit `old_data`/`new_data` and unused moderation `comment_likes(user_id)` selections. Keep full audit storage unchanged.
3. Replace both sermon `select('*')` calls with the fields consumed by `mapSermon`: `id, slug, title, speaker, scripture, series, description, media_type, audio_url, video_url, cover_path, status, preached_at, published_at`.
4. Change the two analytics page callers to publication summaries; keep the admin metrics join and verify all chart/export consumers. Restrict that join to fields actually used (`id, views`) where appropriate.
5. Add public-only data caching with 60-second freshness, plus invalidation on publication/sermon/author/topic changes and scheduled publication transitions. Include profile edits that affect public biographies. Keep auth and personalized reads outside that cache. Catch failures outside cached loaders so failures do not become cached empty libraries.
6. Make notification polling visibility-aware with in-flight protection and failure backoff. Keep normal visible-tab freshness.

Items 1–4 are straightforward payload reductions. Items 5–6 need cache/polling checks. Database aggregation, pagination, related-ranking SQL, and image variants are separate follow-up patches because they touch more behavior. The first patch is now applied locally; database-side topic filtering remains deferred.

For this project's current Next.js configuration (without Cache Components), explicit data caching can use `unstable_cache`; request-only deduplication can use React `cache`. They solve different problems. See [Next.js caching guide](https://nextjs.org/docs/app/guides/caching-without-cache-components) and [unstable_cache](https://nextjs.org/docs/app/api-reference/functions/unstable_cache). Enabling a different rendering architecture is unnecessary for this first patch.

## Request inventory and existing safeguards

| Surface | Current behavior / assessment |
| --- | --- |
| Publication lists/details/related, sermon lists/details, authors, topics | Centralized in `src/lib/data.js`; findings above. Summaries already exist but still fetch complete `import_metadata`; project only tags/categories where required. Legacy redirects currently retrieve full articles just to discover the canonical slug; a slug-only lookup is sufficient there. |
| Homepage | Already uses summaries and `revalidate = 60`. Latest section displays 12, but the archive carousel randomly chooses seven from older content. A blanket homepage limit of 12 would break that feature. Cache the existing summary pool first; optimize sampling separately while preserving its selection rules. |
| Other public pages | Many declare 60-second route revalidation. Do not claim every visit runs every query. Cross-route data reuse and dynamic article pages are the main cache opportunities. No write route currently calls `revalidatePath`/`revalidateTag`. |
| Search | `src/lib/search.js`: one bounded search RPC plus topic/author queries limited to eight each; resource search is local. SQL returns summary columns, not bodies, even though it searches bodies internally. Navbar search is debounced and abortable. `/api/search` has CDN cache headers; `/search` calls the helper directly. Shared caching by normalized query, limit, offset could benefit both. Do not cache error results. |
| Notifications | Each successful poll makes four data reads (three lists capped at eight plus notification states), plus a profile read and normally an authenticated user check. At an uninterrupted 30-second cadence that is 120 polls/hour/tab, or 600 database reads/hour plus roughly 120 auth calls; background browser throttling can lower this. Byte impact depends on payloads. |
| Article interactions | Bounded single-user like/bookmark lookups and user-initiated mutations; comment reads are unpaged. `select('*', { count: 'exact', head: true })` for total likes returns no row bodies and is not a wildcard payload problem. |
| Article/sermon event endpoints | Small insert responses; auth lookup can add requests for signed-in users. Article page-view effect depends on `article.id`, not every render. Sermon tracking already deduplicates by sessionStorage. Do not remove analytics or redefine views just to reduce calls. Raw event rereading by dashboards is a stronger egress concern. |
| Admin content mutations/search | Publication, sermon, author, topic, comment, profile, and settings routes mostly return acknowledgements or selected fields. Admin publication search is debounced and limited to five. Topic creation's wildcard returns one small row; a minor cleanup, not a likely GB-scale cause. Profile updates are split for social-schema compatibility; preserve that behavior unless schema is verified. |
| Admin supporting reads | Tasks: limited to eight. Email history: 50, wildcard. Settings: key/value projection. Current profile/author: single-row wildcards. Moderation/subscribers: unpaged. Notification/reminder state: per-user; reminders use a single-row lookup. Optimize lists before small single-row reads. |
| Auth / invitation / account | Auth actions, callback exchange, reset-password, account/onboarding, middleware, staff checks, and layout are request/action-driven. Browser client is a singleton. Middleware only matches admin/account/auth paths. Preserve its permission checks; avoid shared auth caching. No browser database subscription loop found. |
| Newsletter | Subscription selects one subscriber and one token; unsubscribe is an update. Send helpers fetch all active recipients with explicit columns when an email is sent. Batched cursor iteration would avoid row-cap omissions and excessive memory, but all intended recipients still need processing. Resend requests are external, not Supabase media egress. |
| Images | Admin upload stores original bytes and does not set explicit cacheControl. WordPress import already sets one-year cacheControl but uses upsert on a URL-derived path; changed bytes under the same URL can become stale. Use content-versioned names for new variants. `getPublicUrl` constructs a URL; the browser's subsequent download incurs egress. Local `/images` caching in `next.config.js` does not set headers on remote Supabase images. |
| Sermon audio/video | Public audio uses `preload="metadata"`; direct video does not specify preload. Only media actually hosted on Supabase contributes its media bytes there. `/api/sermons/[id]/audio` proxies **cpmfiles1.com**, so its audio stream is not Supabase Storage traffic; it does perform a small sermon URL lookup for each request/range. Any shared cache must exclude draft/staff-only media. Consider conservative preload only after checking duration/playback behavior. |
| ESV / UI timers | ESV upstream has one-day caching and API cache headers; it is an external service. Hero and archive intervals only change UI state and do not query Supabase. Leave them unchanged. |
| Maintenance scripts | Seed, WordPress import, author provisioning, and admin promotion run from scripts; no scheduled execution found in project configuration. Most operations write with minimal returned data. Import downloads WordPress media, uploads to Storage, and reads narrow lookup columns. No reason to run these scripts during this audit. Repeated external execution would require separate log evidence. |
| Realtime | No app `.channel()` subscriptions or Realtime listener loops found. |

## Validation after approval

- Use mocks/local fixtures first while quota is restricted. Run lint and relevant targeted tests; avoid a production-data build until its network behavior is controlled.
- Compare archive cards, category changes, featured items, topic availability, author pages, detail bodies, and legacy redirects before/after.
- Verify public cache hits across requests, expiry, mutation invalidation, error recovery, and two-user isolation for likes/bookmarks/admin content.
- Verify visible-tab notification freshness, hidden-tab pause, resume, no overlapping requests, and failure backoff.
- Compare analytics totals, custom range boundaries, charts, and CSVs against the existing calculations using the same fixtures before replacing raw-event reads.
- For paging, cover empty results, last page, ties in sort columns, filter changes, and datasets above the configured API row cap. Preserve the existing UI.
- For media, compare actual response bytes and image appearance at mobile/desktop sizes. Check playback, seeking, and downloads. Browser compression of the site's HTML does not shrink the separate Supabase-to-server response.

## Production evidence needed to attribute the 5.79 GB

In the organization's Usage Dashboard, select this project and billing cycle, then compare Database, Storage, Auth, and other egress categories, including cached versus uncached Storage. Correlate spikes with deploys, imports, admin sessions, bots, and popular media. Only then estimate savings in GB. The notice is organization-level and does not by itself prove that this repository caused all usage.

After service resumes, sample a small number of representative requests and compare upstream response sizes, request counts, and cache hits before/after. Do not crawl the whole site or bulk-download Storage to measure it.
